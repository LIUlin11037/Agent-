# AI Prompt 与问题解决记录

这份文档记录三件事：**我怎么用 AI 写这个 Agent**、**哪些 AI 产出被我改掉了**、**踩过的坑怎么修的**。
不是事后总结的漂亮话——每条都能在仓库里找到对应的文件、函数或测试用例。

- Prompt 数量：12 类任务提示词，另有 4 版 Agent 自身 system prompt、4 版压缩提示词
- 人工修正：AI 初版代码有 7 处被推翻重写（见第 4 节）
- 问题记录：20 条 + 外部审查后的 4 条主修正与 4 处名实不符，多数不是设计时想到的，而是跑测试或二次审查时才暴露的

---

## 一、工作方法：先定契约，再让 AI 写实现

四条规矩，贯穿全程：

1. **接口由人定，实现由 AI 铺**。数据结构、终止条件、异常策略我先写死，AI 只负责把边界补全。
   比如 `Decision(kind=final|tool_calls|invalid)` 这个三态是我定的，AI 一开始想返回 `Optional[ToolCall]`，
   被我否了——"解析失败"必须是独立状态，否则没法做修复重试。
2. **每个 prompt 必须要求 AI 给反例**。只让它"实现 X"，它会给你一条 happy path；
   要求"列出会让这段代码出错的输入"，才会得到真正有用的东西。
3. **先写测试，再写实现**。解析器、压缩、循环终止都是先有 `test_*.py` 里的用例，再补代码。
   这样 AI 改实现时不会悄悄改掉语义。
4. **AI 给的方案必须能解释"为什么不用另一个"**。解释不出来的，一律重问。

分工比例大致是：架构与取舍 100% 人工，边界情况 70% 靠 AI 穷举，重复代码 90% 由 AI 生成，
测试用例 60% 由 AI 铺开后再人工补关键断言。

## 二、Prompt 全记录

> 格式统一为：**场景 → Prompt 原文 → AI 给了什么 → 我怎么处理 → 落到哪**。
> Prompt 原文可直接复制复用。

### P1 把题目拆成可验收的检查项

**场景**：刚拿到题，先不做设计，先找"写得不清楚但会扣分"的地方。

```
把下面这段需求拆成可验收的检查项，重点标出「写得不清楚但会扣分」的地方。

要求：
1. 输出四列：模块 / 必须交付 / 可能的理解分歧 / 容易被忽略的细节
2. 对每个理解分歧，给出两种读法，并说明哪一种更容易被面试官接受
3. 单独列出「如果我只做最小区间，哪些点一定会被扣分」

题目全文：
[粘贴题目]
```

**AI 给了什么**：一张 12 行的表。关键的三条分歧是：

| 分歧点 | 读法 A | 读法 B |
|---|---|---|
| 两个窗口"互不影响" | 连待办也隔离 | 只隔离对话，待办是用户资产 |
| "解析 LLM 输出" | 只解析原生 tool_calls | 还要自己处理文本协议 |
| "最大轮次限制" | 单轮工具步数上限 | 整个会话的轮数上限 |

**我怎么处理**：三条都没有二选一，而是"都做，且可配置/可解释"：

- 待办做成 `AGENT_TODO_SCOPE=user|session`，默认共享，两种语义都有测试（`test_todo_shared_across_windows` / `test_todo_isolated_when_scope_is_session`）
- 解析做成双协议，trace 里记 `protocol=native|text|fallback`
- "最大轮次"拆成两层：单轮 `AGENT_MAX_STEPS=8` + 跨轮上下文压缩

**落到哪**：README「设计取舍」一节，就是这次 prompt 的直接产物。

### P2 主循环骨架：先要状态机，不要代码

**场景**：核心循环必须自己写，先让 AI 把"所有可能的出口"列全，而不是直接生成 `while True`。

```
我要手写一个 Agent 主循环，不依赖任何框架。请先不要写代码，按下面步骤输出：

1. 用伪代码写出一次用户输入到最终回复的完整流程
2. 列出所有可能的终止路径，每条注明「触发条件」和「用户应该看到什么」
3. 列出所有可能让循环卡死或空转的情况，以及检测方式
4. 指出哪一步最容易写出 bug

约束：
- 工具执行结果必须回填进上下文，再让模型决定下一步
- 任何异常都不能让进程崩掉
- 不允许出现没有上限的 while
```

**AI 给了什么**：伪代码 + 5 条终止路径（final / max_steps / 工具连续失败 / 模型不可用 / 解析失败）。
它建议"工具连续失败 3 次就停"，我否了——失败也可能是模型在试错，应该把错误回喂让它自己改。

**我怎么处理**：保留 4 条终止路径，新增 `loop_guard`（相同 `(工具, 参数)` 重复调用）：

```
final     模型给出最终答案
max_steps 单轮工具步数达到上限
loop_guard 同一工具同一参数累计 3 次
error     模型不可用 / 连续两次无法解析
```

**落到哪**：`agent/runtime.py::chat` 的四个 return 分支，`ChatResult.stopped_reason` 一一对应。

### P3 解析器：穷举会让解析失败的输入

**场景**：解析层是"自己实现 Runtime"最容易被质疑的部分，必须证明它不是只处理了标准格式。

```
我在实现一个把 LLM 输出解析成三态的解析器：
  tool_calls（要调工具）/ final（最终答案）/ invalid（无法解析）
支持两条协议：
  A. 原生 function calling：响应里有 tool_calls 字段，arguments 是 JSON 字符串
  B. 文本协议：模型在正文里输出 ```json {"tool": "...", "arguments": {...}} ```

请列出所有可能让解析失败的输入形态，按「真实模型会输出的概率」从高到低排序。
每种给出：
1. 一个最小复现样例（真实一点，别用 aaa/bbb）
2. 解析器应该怎么处理（修复 / 降级 / 判 invalid）
3. 如果判 invalid，回喂给模型的提示应该说什么
```

**AI 给了什么**：23 种形态。高概率的包括：

- arguments 是字符串而不是对象（`"arguments": "{\"city\": \"北京\"}"`）
- JSON 前后夹着解释文字（"好的，我来查一下：{...}"）
- 尾逗号、单引号、`True/False`（Python 字面量风格）
- 代码块没闭合
- 一次返回多个 tool_calls
- 中文思考标签 `<thinking>...</thinking>` 混在正文里
- 空响应、只有空白

**我怎么处理**：全部实现，但拒绝了两条 AI 的建议：

| AI 建议 | 我的判断 |
|---|---|
| 用正则 `\{.*\}` 抓 JSON | 嵌套对象和字符串里的花括号会截错，改成手写括号配平扫描 `_first_json_object()` |
| 解析失败就直接返回错误给用户 | 太脆。改成先追加一条纠正提示重试一次（`REPAIR_HINT`），二次失败才降级 |

**落到哪**：`agent/parser.py` 的 `loads_lenient` / `_first_json_object` / `_coerce_arguments`；
用例 `tests/test_parser.py` 17 条，覆盖上表全部形态。

### P4 工具注册与参数校验：不引第三方库

**场景**：题目要求"名称 + 描述 + 参数 Schema"，且模型要能基于 Schema 决策。很多人会直接装 `jsonschema`，
但这里刻意手写，因为报错信息要能直接回喂给模型。

```
实现一个工具注册机制：
- 装饰器注册，每个工具声明 name / description / parameters(JSON Schema 子集)
- 能自动转成 OpenAI function calling 的 tools 描述
- 执行前按 Schema 校验参数，校验失败不抛异常，返回结构化错误

校验器请手写，不要用 jsonschema 库。只支持本项目用到的子集：
type / required / enum / minimum / maximum / minLength / maxLength /
minItems / maxItems / items.type / additionalProperties=false

关键要求：错误信息必须是中文、可读、能直接拼进下一轮 prompt 让模型自己改。
请给出 5 条真实会出现的错误参数，以及对应的报错文案。
```

**AI 给了什么**：可用实现，但错误文案是英文模板（`'city' is not of type 'string'`），
且 `bool` 被当成 `integer` 通过了校验。

**我怎么处理**：
- 文案全部改成"参数 `city` 类型应为 string，实际是 int"这种可直接读的句子
- 补 `bool is not int` 的特判（Python 里 `isinstance(True, int)` 是 `True`，这是个经典坑）
- 加 `additionalProperties=false` 的拒绝逻辑，防止模型塞无关字段

**落到哪**：`agent/tools/base.py`；用例 `test_registry.py` 14 条，含 `test_validate_bool_is_not_integer`。

### P5 calculator：禁用 eval，但要能算

**场景**：题目只要求"calculator"，最省事的写法是 `eval()`。这在我这里是红线。

```
实现一个计算器工具，要求：
1. 绝对不能用 eval / exec / compile
2. 支持 + - * / // % **、括号、一元正负号
3. 支持 abs/round/min/max/sum/sqrt/log/log10/exp/floor/ceil/pow
4. 中英文符号都要能处理：× ÷ ^ （ ） ，
5. 指数爆炸要拦：2**1000000 不能把进程卡死
6. 除零、语法错误要给用户能看懂的中文错误

然后请列出 10 个攻击输入，验证这个实现确实无法执行任意代码。
```

**AI 给了什么**：AST 遍历实现 + 攻击用例。攻击清单里有 `__import__('os').system('...')`、
`(1).__class__.__bases__`、`open('/etc/passwd')`、`lambda: 1`、`[x for x in range(10**9)]`。

**我怎么处理**：实现基本可用，补了两点：
- 指数上限 `abs(right) > 64` 直接拒绝（AI 原来只限制了输入长度）
- 结果格式化：整数不显示 `.0`，`NaN/Inf` 给中文提示而不是抛出去

**落到哪**：`agent/tools/calculator.py`；`test_tools.py` 里 7 条计算器用例，含注入拦截。

### P6 上下文怎么放：让 AI 给三种方案并互相攻击

**场景**：题目明确问"哪些信息要塞进 context"。这题没有标准答案，关键是取舍能自圆其说。

```
一个多轮 Agent 的上下文里，可能要放这些东西：
system prompt、历史原文、历史摘要、当前时间、用户待办、
上一次工具调用的参数与结果、模型的思考过程、用户画像。

请给三种不同的放置方案（不是三种格式，是三种取舍哲学），
然后让这三种方案互相攻击：每种方案在「用户追问」场景下会怎么失败？
最后给出你的推荐，以及推荐方案最可能被质疑的点。
```

**AI 给了什么**：三种方案——"全量原文"、"摘要优先"、"状态优先"。
互相攻击的结论很有用：
- 全量原文：长会话必然爆 token
- 摘要优先：摘要一旦丢了数字/待办，追问就答错，且无法恢复
- 状态优先：状态块每次重建，成本低，但"状态提取规则"如果写错，会持续误导模型

**我怎么处理**：选"状态优先 + 原文兜底"的混合方案，顺序固定为：

```
1. system（角色 + 工具规范 + 输出格式）
2. 历史摘要（只在压缩时重写）
3. 状态块（时间 / 未完成待办 / 上次工具调用 / 已知事实）—— 永不压缩
4. 最近 N 轮原文
```

并明确一个反直觉决定：**模型的思考过程不进上下文**。它只在当轮有用，跨轮保留既费 token 又容易让模型
重复上一轮的思路。所以 `reasoning` 只落库、只进 trace，不进 messages。

**落到哪**：`agent/context.py::ContextBuilder.build`；README 第 5 节的两张表就是这次 prompt 的结论。

### P7 压缩：要求 AI 先给失败模式，再给提示词

**场景**：压缩最容易做成"总结一下"，然后丢关键信息。所以先问失败模式。

```
我要给多轮对话做基础压缩：超过阈值时，把早期轮次压成摘要，保留最近 N 轮原文。
压缩本身也是一次 LLM 调用。

请先回答：
1. 一个"看起来正常"的摘要，可能丢掉哪些对追问致命的信息？
2. 压缩应该按消息条数切，还是按轮切？为什么？
3. 压缩失败（LLM 超时/返回空）时，主流程应该怎么办？
4. 写出压缩用的 system prompt 和 user 模板，要求摘要不超过 400 字。

约束：摘要会和已有摘要滚动合并；工具调用的结论不能丢。
```

**AI 给了什么**：失败模式列得很准——丢数字、丢"用户否定了什么"、丢未完成事项、把寒暄也压进去。
但第一版模板只写了"请总结以下对话"，我要求重写。

**最终用的模板**（`agent/context.py::COMPRESS_TEMPLATE`）：

```
已有摘要：
{summary}

需要并入摘要的新对话：
{chunk}

要求：
1. 合并去重，输出一份新的摘要，不超过 400 字。
2. 必须保留：用户的目标与偏好、已确认的事实与数字、已完成事项、
   未完成或待跟进事项、重要工具调用的结论。
3. 丢弃寒暄、重复内容和被否定的中间尝试。
4. 用短句和分号连接，不要分点标题。
```

**我怎么处理**：按"轮"切（`group_turns`），不按条切——否则会把 `assistant.tool_calls` 和
对应的 `tool` 结果拆开，下一轮请求直接非法。压缩失败退化为机械摘要，绝不中断主流程。

**落到哪**：`agent/context.py::maybe_compress` / `_mechanical_summary`；
用例 `test_compression_triggers_and_keeps_raw_messages`、`test_compression_failure_falls_back`、
`test_follow_up_survives_compression`。

### P8 会话表设计：先让 AI 画生命周期

**场景**：窗口隔离不是"每个窗口一个 list"，要能重启恢复、能压缩、能审计。

```
设计 SQLite 存储，支持：
1. 同一用户多个窗口，上下文互不可见
2. 进程重启后能恢复：消息、摘要、压缩进度、待办
3. 压缩后原始消息不能删（要能审计/回放）
4. 待办可能跨窗口共享，也可能按窗口隔离（可配置）

请输出：
- 表结构（字段、索引、为什么需要这个字段）
- 每个字段的写入时机
- 「压缩进度」怎么表示，才能让恢复后的上下文和压缩前一致
- 你认为最容易设计错的一处
```

**AI 给了什么**：三表方案（sessions / messages / todos），关键设计是 `compressed_upto` 水位线 +
`messages.seq` 单调递增，恢复时用 `seq > compressed_upto` 过滤。这正是我想要的。

**我怎么处理**：采纳，但补了两处：
- `todos.owner` 不存 user_id，而存"归属键"（`todo_owner()`），user 级就是 user_id，session 级就是 session_id——一张表支持两种语义
- 所有写操作加 `RLock`，连接用 `check_same_thread=False`（Web 场景会跨线程）

**落到哪**：`agent/session.py` 的建表 SQL 与 `todo_owner`；`test_session.py` 12 条用例。

### P9 测试矩阵：要离线、要能断言"上下文里有什么"

**场景**：没有 API Key 也要能跑全量测试，且不能只断言最终文本（模型可以蒙对）。

```
这是一个自实现 Agent Runtime，LLM 和工具都可注入。请设计一套完全离线、不需要 API Key 的测试。

要求：
1. 覆盖：主循环终止条件、解析失败、工具异常、会话隔离、上下文压缩、追问
2. 用 FakeLLM 脚本化回放模型响应，脚本耗尽要报错，不能静默通过
3. 断言要检查「第二次请求的 messages 里有什么」，而不是只看最终回复
4. 列出每个用例的「构造方式 + 断言什么」，先给表，不要写代码
```

**AI 给了什么**：测试矩阵 + FakeLLM 设计。它提出的"检查第二次请求是否包含 tool 消息"这个思路很好，
比断言最终文本可靠得多。

**我怎么处理**：采纳矩阵，补了三个它没想到的：
- `SummaryLLM`：压缩调用会插在正常对话之间，会打乱脚本顺序，必须单独识别
- 工具报错后模型自愈的用例（回喂错误 → 模型换参数 → 成功）
- 循环守卫的用例（同一调用重复 3 次必须被打断，且第 2 次要先给提示）

**落到哪**：`tests/` 共 105 条离线用例 + 3 条真实模型用例（默认 skip）。

### P10 让 AI 当面试官：按扣分概率挑毛病

**场景**：功能写完、测试全绿之后，最危险的是"自己看不出问题"。这轮 prompt 直接找出了 3 个真 bug。

```
你现在是这次笔试的面试官，要在 30 分钟内判断这份代码能不能过。请按「扣分概率」从高到低列出问题。

重点检查：
1. 题目里的每条要求，是否真的实现了，而不是 README 里写了
2. 有没有"看起来隔离，实际能绕过"的地方（session、用户、文件路径）
3. 测试是否在自我安慰（只测 happy path、断言太弱）
4. 异常路径是否真的跑过

对每个问题给出：复现步骤、影响、修复建议、应该补什么测试。
不要夸，只挑毛病。
```

**AI 给了什么**：第一轮自查给了 11 条，其中 3 条是真问题（第二轮外部审查又发现 4 条，见第八节）：

1. **换个 user_id 传同一个 session_id 就能接管别人的窗口**——`ensure_session` 只按 id 查，不校验归属
2. **session_id 被直接拼进 trace 文件名**——传 `../../x` 可以写到仓库外
3. **并行工具调用时 loop_guard 失效**——重复计数用的是"上一个 key"，第二个 key 每次都重置计数

**我怎么处理**：三个都修了，并各补了用例：

| 问题 | 修法 | 用例 |
|---|---|---|
| 跨用户接管 | `ensure_session/get_session` 增加 `user_id`，不符抛 `SessionAccessDenied`，Web 映射 403 | `test_other_user_cannot_continue_session`、`test_messages_endpoint_rejects_other_user` |
| 路径穿越 | id 走白名单 `^[A-Za-z0-9_-]{1,64}$`，trace 接口先校验归属 | `test_invalid_session_id_rejected`、`test_trace_endpoint_rejects_path_traversal` |
| 并行 loop_guard | 改成 `dict[fingerprint] -> count`，取最大计数判断 | `test_loop_guard_handles_parallel_calls` |

**落到哪**：`agent/session.py`、`agent/runtime.py`、`server.py`；对应问题记录第 9-11 条。

### P11 文档：让读者 5 分钟判断"是否满足要求"

**场景**：README 不是写给自己看的，是给要打分的陌生人看的。

```
写 README，读者是「要在 5 分钟内判断这份作业是否合格」的面试官。要求：

1. 第一屏就要能看出：不用框架、实现了什么、怎么跑起来
2. 必须有「需求 → 实现位置 → 验证用例」的对照表
3. 单独一节讲上下文管理：放了什么、什么时候召回、为什么这么放
4. 诚实写「已知限制」，不要藏
5. 不要用"强大、优雅、高性能"这类形容词，用事实

先给目录结构，我确认后再写正文。
```

**AI 给了什么**：结构可用，但初版有一堆"企业级、高可用"的空话，被我全部删掉。

**我怎么处理**：保留"需求对照表 + 记忆放置/召回两张表 + 已知限制"，
把"设计取舍"单独成节，专门解释三个反直觉决定（todo 归属、状态块前置、不用向量检索）。

**落到哪**：`README.md`。

### P12 真实模型跑挂时，怎么让 AI 帮你定位

**场景**：留一个可复用的排查模板。真实调用出问题时，日志比猜测有用。

```
这是我的一次真实调用 trace（JSONL，已脱敏）：
[粘贴 trace 中 user_input / llm_request / llm_response / parse / tool_call / tool_result]

现象：[例如：模型没调工具，直接编了一个天气]

请按顺序判断：
1. 是 prompt 没说清，还是工具 Schema 让模型看不懂？
2. 是模型不支持 function calling，走了文本协议但格式不对？
3. 是工具返回太长被截断，导致模型误判？
4. 给出最小修改：改 prompt 的哪一句 / 改 Schema 的哪个字段 / 改代码的哪一行

不要给多个方案让我选，直接给最可能的一条，并说明怎么验证。
```

**用途**：把"模型不听话"拆成可验证的假设。这套流程后来固化成 trace 事件序列，
`/trace` 命令和 Web 的轨迹面板都能直接看到。

## 三、Agent 自身的提示词：四个版本

这是这个项目里最像"产品"的部分。`SYSTEM_PROMPT` 改过 4 版，每版都是被真实问题逼出来的。

### v1：只有角色

```
你是一个中文助手，可以调用工具帮助用户。
```

**问题**：问"1+1 等于几"也要走一遍 calculator，明明一步能答的事拖成两步；工具报错后模型开始编答案。

### v2：加"不要为调用而调用"

新增两句：

```
能直接回答的就直接回答，不要为了调用工具而调用工具。
绝不编造工具结果。工具报错时，根据错误信息修正参数重试，或如实告知用户。
```

**效果**：闲聊类问题不再乱调工具；工具失败后的胡编明显减少。

### v3：加"追问规则"

这条是"带工具的追问"能不能成立的关键：

```
用户追问省略了主语或地点时，参考【会话状态】里的「上次工具调用」补全参数。
```

**注意**：这句话必须和状态块里的字段名严格对应（`上次工具调用`）。prompt 里写"参考上文"是没用的，
模型不知道"上文"指哪一行。

### v4：加文本协议格式（当前版本）

```
若当前接口不支持 function calling，请只输出一个 JSON 对象：
{"tool": "工具名", "arguments": {...}}
需要直接回答时，正常输出文本即可。
```

**为什么放在 system prompt 里**：不是所有模型都稳定支持 function calling；把格式写死在 prompt 里，
文本协议这条兼容路径才可用。代价是 system prompt 长了约 60 字，换来的是"换模型不用改代码"。

### 当前完整版（`agent/context.py::SYSTEM_PROMPT`）

```
你是一个可靠、克制的中文助手，运行在一个自行实现的最小 Agent Runtime 上。

工作方式：
1. 能直接回答的就直接回答，不要为了调用工具而调用工具。
2. 需要外部信息（算术、资料检索、天气、待办、文档）时调用对应工具；一次可以调用多个。
3. 拿到工具结果后判断是否还需要继续调用；信息足够时立即给出最终回答。
4. 绝不编造工具结果。工具报错时，根据错误信息修正参数重试，或如实告知用户。

工具使用规范：
- 任何算术都用 calculator，不要心算。
- 查公司制度/流程先用 search，需要全文再用 read_docs。
- 用户说「记一下 / 待办 / 提醒我」用 todo 的 add；说「做完了」用 done。
- 用户追问省略了主语或地点时，参考【会话状态】里的「上次工具调用」补全参数。

输出要求：
- 简体中文，结论先行，简洁。
- 若当前接口不支持 function calling，请只输出一个 JSON 对象：
  {"tool": "工具名", "arguments": {...}}
  需要直接回答时，正常输出文本即可。
```

### 压缩提示词的演进

| 版本 | 写法 | 出的问题 |
|---|---|---|
| v1 | "请总结以下对话" | 摘要里全是"用户询问了天气"这种废话，数字和待办全丢 |
| v2 | 加"保留数字、待办、未完成事项" | 摘要开始变长，经常 800 字以上，压缩没意义 |
| v3 | 限 400 字 + "合并去重" | 开始丢掉"用户否定过的方案"，追问时重复推荐被否的东西 |
| v4（当前） | 加"丢弃寒暄、重复内容和被否定的中间尝试"，要求短句分号连接 | 稳定 |

**一条经验**：压缩提示词里，"保留什么"必须写成**可枚举的清单**（数字/待办/未完成/工具结论），
写"保留重要信息"等于没写。

## 四、AI 生成代码的人工修正清单

这部分是"AI 辅助"最该保留的证据：哪些是 AI 写的、哪里不能用。

| # | AI 初版 | 问题 | 人工改成 | 位置 |
|---|---|---|---|---|
| 1 | `eval(expression)` | 任意代码执行 | AST 白名单遍历，禁用属性访问/导入/lambda | `tools/calculator.py` |
| 2 | 正则 `\{.*\}` 抓 JSON | 嵌套对象、字符串内花括号会截错 | 手写括号配平扫描，跳过字符串与转义 | `parser.py::_first_json_object` |
| 3 | `messages[-N:]` 截断历史 | 会把 `assistant.tool_calls` 和对应 `tool` 结果拆开，请求非法 | 按"轮"切分，整轮保留或整轮压缩 | `context.py::group_turns` |
| 4 | 解析失败直接报错 | 模型偶尔吐畸形 JSON 就整轮失败 | 追加纠正提示重试一次，二次失败才降级 | `runtime.py::REPAIR_HINT` |
| 5 | `isinstance(v, int)` 校验 integer | `True` 会被当成 1 放过去 | 先排除 `bool` | `tools/base.py::_check_type` |
| 6 | `ensure_session(id)` 只按 id 查 | 换个用户就能接管别人的窗口 | 加 `user_id` 归属校验 | `session.py` |
| 7 | `trace_dir / f"{session_id}.jsonl"` | `../` 路径穿越 | session_id 白名单校验 | `session.py::validate_session_id` |

共同点：**AI 的默认实现几乎总是"功能正确、边界错误"**。所以每个模块我都配了异常路径的测试，
而不是只测"能不能跑通"。

## 五、问题解决记录（20 条，另有第八节的外部审查补充）

按主题分组。每条都是"现象 → 原因 → 解法 → 验证"，能复现。

### A. 循环与解析

#### 1. 模型陷入重复调用死循环

**现象**：工具返回"没有找到"，模型原样再调一次同样的参数，反复循环直到步数耗尽。

**原因**：只靠 `max_steps` 兜底，用户体验是"转了 8 步然后说失败了"。

**解法**：加重复调用检测。用 `(工具名, 排序后的参数 JSON)` 做指纹：第 2 次重复时注入提示
（"结果不会变化，请基于已有结果作答"），第 3 次**在执行前拦截**，返回 `stopped_reason=loop_guard`——写工具不会被重复执行。

**验证**：`test_loop.py::test_loop_guard_breaks_repeat`、`test_loop_guard_blocks_before_side_effect`（写工具只落两条）。

#### 2. 并行工具调用让死循环检测失效

**现象**：模型一步并行调 `weather(北京)` + `weather(上海)`，每步完全重复，`loop_guard` 却从不触发。

**原因**：重复计数用的是"上一个 key"，第二个 key 每次都把它重置成 1。

**解法**：改成 `dict[fingerprint] -> count`，一步结束后取最大计数判断；提示只对同一指纹发一次。

**验证**：`test_loop.py::test_loop_guard_handles_parallel_calls`。

#### 3. `str.format` 与 JSON 花括号冲突

**现象**：解析失败触发修复提示时抛 `KeyError: '"tool"'`，整个对话崩掉。

**原因**：模板里写了 `{"tool": "工具名"}`，`str.format()` 把 `{"tool"` 当占位符。

**解法**：字面花括号转义成 `{{` `}}`。

**教训**：异常处理路径本身也要有测试。这个 bug 只在"模型输出无法解析"时触发，正是最容易漏测的分支。

#### 4. 文本协议只认 `{"tool": ...}`，不认 ReAct 风格

**现象**：部分模型输出 `{"thought": "...", "action": "weather", "action_input": {...}}`，
解析器整段 JSON 当成最终答案回给用户。

**解法**：`action` 不在 `final/answer/respond/tool/call/use` 里、且带参数键时，把 `action` 当工具名；
`action_input` 加入参数键候选。边界：只有 `action` 没有参数时不瞎猜。

**验证**：`test_parser.py::test_text_protocol_react_style_action` /
`test_text_protocol_action_without_arguments_is_final`。

#### 5. 消息顺序非法导致 API 400

**现象**：压缩后偶发请求失败，报 `messages with role 'tool' must be a response to a preceding message with 'tool_calls'`。

**原因**：最初按"消息条数"截断，正好切在 assistant 和 tool 之间。

**解法**：`group_turns()` 以 user 消息为界切轮，一轮内部的 assistant / tool / assistant 整体保留或整体压缩；
水位线记录到"最后一轮最后一条消息的 seq"。

**验证**：`test_context.py::test_group_turns_keeps_tool_pairs`。

### B. 工具与安全

#### 6. `__import__('os').system(...)` 能被执行

**现象**：calculator 初版用 `eval`，注入测试直接拿到 shell。

**解法**：换成 AST 白名单：只允许数字常量、二元运算、一元正负、白名单函数调用；
属性访问、下标、lambda、推导式一律拒绝；指数绝对值限制 64。

**验证**：`test_tools.py` 中的注入拦截用例。

#### 7. 工具输出过长撑爆上下文

**现象**：`read_docs` 返回整篇文档，下一轮请求 token 直接翻倍。

**解法**：`execute_tool` 统一按 `AGENT_MAX_TOOL_OUTPUT`（默认 4000 字符）截断，
并在末尾注明"原始长度 N 字符"，让模型知道被截断了。

**验证**：`test_registry.py::test_long_output_truncated`。

#### 8. 工具内部异常把主循环带崩

**现象**：工具里一个 `KeyError` 直接冒泡到 `chat()`，用户看到堆栈。

**解法**：`execute_tool` 捕获所有异常，收敛成 `ToolResult(ok=False)`；错误文本拼成
`[工具执行失败] ... 请修正参数或如实告知用户` 回喂，让模型自愈。

**验证**：`test_loop.py::test_tool_error_is_fed_back_and_recovers`。

### C. 会话与存储

#### 9. 换个用户传同一个 session_id，就能接管别人的窗口

**现象**：`ensure_session(user_id, session_id)` 只按 id 查会话，不校验归属。
`chat("user_b", ..., session_id="win1")` 会接着 `user_a` 的窗口聊，`history("win1")` 也能读走全部历史。

**原因**：把"窗口隔离"理解成"每个 id 一份上下文"，漏掉了 id 是用户可控输入。

**解法**：`ensure_session` / `get_session` 增加 `user_id` 参数，归属不符抛 `SessionAccessDenied`；
Web 层映射 403；CLI 的 `/history` 带当前用户。

**验证**：`test_other_user_cannot_continue_session`（同时断言原会话没被污染）、
`test_server.py::test_messages_endpoint_rejects_other_user`。

#### 10. session_id 拼进 trace 文件名 = 路径穿越

**现象**：传 `session_id="../../server"` 能把日志写到仓库外；Web 的 trace 接口反过来能读任意 `.jsonl`。

**解法**：入口统一白名单 `^[A-Za-z0-9_-]{1,64}$`；trace 接口先校验会话归属再拼路径。

**验证**：`test_invalid_session_id_rejected`、`test_trace_endpoint_rejects_path_traversal`。

#### 11. 待办到底属于窗口还是用户

**现象**：题目说"两个窗口互不影响"，但用户换窗口看不到刚才记的待办，体验很怪。

**解法**：不替产品做决定，做成配置。默认 `AGENT_TODO_SCOPE=user`（对话隔离、待办共享），
可切 `session`（严格隔离）。两种语义都有测试。

**验证**：`test_todo_shared_across_windows` / `test_todo_isolated_when_scope_is_session`。

#### 12. Web 场景下 SQLite 跨线程报错

**现象**：`uvicorn` 多线程处理请求时偶发 `SQLite objects created in a thread can only be used in that same thread`。

**解法**：连接加 `check_same_thread=False`，所有读写套 `RLock`。单机演示足够，不引入连接池。

### D. 上下文与压缩

#### 13. 摘要把"被否定的方案"也保留了，模型反复推荐

**现象**：用户说过"不要用 A 方案"，压缩后摘要里只留下"A 方案"，下一轮模型又把 A 推了一遍。

**原因**：压缩提示词只要求"总结对话"，模型倾向于保留出现过的名词，丢掉否定语气。

**解法**：模板里显式写"丢弃寒暄、重复内容和**被否定的中间尝试**"，并要求保留"用户的目标与偏好"。
两者配合，才能把"不要 A"变成一条可执行的偏好，而不是一段被截断的历史。

**验证**：这条只做了手工验证——跑多轮"先否定再追问"，看摘要里是否出现"用户不要 A"这类表述。
自动化用例只覆盖摘要注入链路（`test_summary_injected_after_compression`），没有单独断言否定语义，
所以这里不把它算成"有测试保证"。

#### 14. 中文 token 估算严重偏低

**现象**：用"字符数 / 4"估算，中文场景压缩从不触发，直到请求超限报错。

**解法**：中英文分权——中文按 1 字 ≈ 1 token，其余按 4 字符 ≈ 1 token。零依赖，够用。

**验证**：`test_context.py::test_estimate_tokens_prefers_cjk`。

#### 15. 假模型被压缩调用打乱脚本

**现象**：压缩测试里 `FakeLLM` 脚本顺序错位，断言全挂。

**原因**：压缩发生在装配上下文时，会插到正常对话调用之间，消耗掉一个脚本项。

**解法**：`SummaryLLM` 先识别"system 是不是压缩提示"，是则返回固定摘要，否则走脚本回放；压缩调用单独计数。

#### 16. 压缩失败不能拖垮主流程

**现象**：压作用的 LLM 调用超时，整个 `chat()` 抛异常。

**解法**：压缩单独 try/except，失败退化为机械摘要（截断保留尾部），水位线照常推进。

**验证**：`test_context.py::test_compression_failure_falls_back`。

#### 17. 压缩后追问断片

**现象**：早期原文被压掉后，"那上海呢"无法补全城市。

**原因**：担心摘要丢信息，但真正起作用的不是摘要，而是状态块里的 `last_tool_call`。

**解法**：状态块永不压缩，每轮从 `session.facts` 重建；摘要只负责"目标和偏好"这类软信息。

**验证**：`test_context.py::test_follow_up_survives_compression`。

### E. 工程环境

#### 18. Windows 下 `pip` 与 `python` 不是同一个解释器

**现象**：`pip install pytest` 成功，但 `python -m pytest` 报模块不存在。

**原因**：`pip` 指向 F:\Python3.10，PATH 里的 `python` 是另一个 3.13 环境。

**解法**：统一用 `python -m pip install ...`。

#### 19. Windows 控制台中文/符号乱码

**现象**：CLI 输出里 `°C`、`→` 显示成问号。

**解法**：启动时 `sys.stdout.reconfigure(encoding="utf-8")`，失败则静默跳过。

#### 20. 离线演示每次重跑，待办越积越多

**现象**：`demo_offline.py` 第二次运行，待办列表里出现两条一样的"周五前交周报"，看不出"隔离"这件事。

**原因**：演示库是持久化的 SQLite。

**解法**：演示启动时重置 `data/demo/demo.db` 与对应 trace。演示数据本来就是一次性产物。

## 六、如果重来，我会怎么改 prompt

1. **先让 AI 列"会怎么失败"，再让它写实现**。P3、P7、P10 的产出质量明显高于直接说"实现 X"的几轮。
2. **给约束，不给形容词**。"简洁"没用，"不超过 400 字、用分号连接"才有用。
3. **要求 AI 标注不确定的地方**。它说"这样可以"的时候，通常有一处没想清楚；让它写"我不确定 X，因为 Y"，
   能提前发现问题。
4. **审查 prompt 要指定角色和输出格式**。"帮我看看代码"会得到客套话；
   "你是面试官，按扣分概率排序，给复现步骤"才会得到真问题。
5. **不要让 AI 同时改实现和测试**。同一轮里改两边，测试会跟着实现走，等于没测。

## 七、可复用模板

**让 AI 穷举边界**

```
我在实现 [模块]，输入来自 [来源]，输出会被 [下游] 消费。
列出所有可能让它出错的输入形态，按真实出现概率排序。
每种给：最小复现样例 / 应该怎么处理 / 如果降级，用户看到什么。
```

**让 AI 自查**

```
你是要给我打分的人。按扣分概率从高到低列出这份实现的问题。
重点看：要求是否真的实现、有没有可绕过的隔离、测试是否在自我安慰、异常路径是否跑过。
每条给复现步骤和该补的测试。不要夸。
```

**让 AI 设计提示词**

```
我要让模型稳定输出 [格式/行为]。
先列出它可能不听话的 5 种方式，再给一版提示词，要求：
约束写成可判定的条件；给出正例和反例；不超过 [N] 字。
```

## 八、外部审查后的 4 条主修正与 4 处名实不符

代码写完后，我把仓库交给另一个模型做只读审查（不让它改代码，也不让它跑测试）。
它按"会不会扣分"排了序，前两条是真 correctness 问题。这一轮的价值在于：
**自己写测试，测的是"我以为的失败模式"；换个模型看，能看到我没设防的地方。**

### 1. 写工具被重复执行（最严重）

**它指出的问题**：`runtime.py` 是先执行工具、再检查重复次数，所以模型连续三次 `todo(add)`
会真的落三条数据，然后才触发 `loop_guard`。只读工具无所谓，写工具是实际副作用。

**修法**：把重复检测提前到执行前。先按 `(工具, 参数)` 算"预计执行次数"，
达到上限就直接返回 `loop_guard`，不再调用工具；同一批里重复出现也算。
提示改为"我准备第 3 次用相同参数调用 X，所以这次没有再执行"。

**验证**：新增 `test_loop_guard_blocks_before_side_effect`，断言库里只有两条待办。

### 2. 压缩会静默丢掉没装进输入的历史

**它指出的问题**：原来把整段冷历史截断到 6000 字符喂给压缩模型，但水位线仍推进到全部冷轮次末尾。
被截掉的部分既不在摘要里，也不再进入活动上下文——原文还在库里，但模型永远看不到了。

**修法**：改成按字符预算分批（6000/批，最多 3 批），每批完整喂进去；
`compressed_upto` 只推进到"真正处理过"的最后一轮，剩下的轮次留在活动上下文里，下次再压。
单条超长消息仍会截断，但会留"（截断）"标记，且只影响单条，不影响整轮。

**验证**：`test_compression_batches_instead_of_dropping_history`，
断言所有被压掉的消息都真的出现在某批压缩输入里，且水位线没有越过后面的历史。

### 3. 坏掉的工具调用被当成最终答案

**它指出的问题**：模型输出被截断的 `{"tool": ..., "arguments": ...`，解析失败后走 fallback，
直接把这段 JSON 当最终答案展示给用户，没有进入修复重试。

**修法**：加一个"像不像工具调用"的判断——正文以 `{` 开头或带 json 代码块，且出现 `tool/arguments`
这类键，就判 `invalid`，交给 runtime 的修复流程。同时收紧 `name` 键：普通 JSON 回答里的 `name`
不再被当成工具名（必须同时带参数键）。

**验证**：`test_broken_tool_json_is_invalid_not_final`、`test_broken_fenced_tool_json_is_invalid`、
`test_plain_json_answer_with_name_stays_final`。

### 4. 追问测试是"信息已提供"，不是"行为已发生"

**它指出的问题**：原来的追问用例断言的是"上次工具调用被注入 system"，第二次回答是脚本预写的，
没有证明 Agent 真的发起了 `weather(上海)`。

**修法**：改用 callable 的 FakeLLM，根据上下文内容决定返回什么：
只有 system 里出现"上次工具调用 + 北京"才返回上海调用，然后断言工具真的执行成功、结果里有"上海"。
纯对话追问也改成"换一个窗口问同样问题，答案必须不同"。

**验证**：`test_tool_follow_up_actually_executes_new_call`、`test_pure_chat_follow_up_uses_prior_turn`。

### 顺带修掉的名实不符

- `config.tool_timeout` 从来没被工具执行器用过 → 直接删掉，不留下"看着有其实没有"的配置
- 每次对话都新建 `Tracer`，导致同一文件的 `turn` 永远是 1 → 初始化时接着已有 `user_input` 事件数往下数
- `ContextBuilder` 创建时没拿到 tracer，正常链路的 `compress` 事件不会进 trace → 每轮把 tracer 注入
- Web 前端读取消息和轨迹时没带 `user_id`，非默认用户会 403 → 两处请求都补上当前用户
